# FlowCraft 协作方案设计（仅设计，不实现）

> 状态：设计文档。当前阶段不实现后端、不同步、不做多人编辑（README「明确不做」）。
> 用途：当确需协作时，作为后端、权限与冲突合并的设计起点，避免临时拍脑袋。
> 前置阅读：[README.md](../README.md) 的数据模型与存储键、[GRAPH.md](../GRAPH.md) 的多画布存储约定。
> 日期：2026-11-02

## 1. 目标与非目标

目标：

- 多人围绕同一个流程图协作编辑与评审（编辑热点：节点/元素/连线/批注/画布列表）。
- 本地优先的平滑过渡：单机体验不变，登录后才进入协作。
- 冲突可解释：合并结果可预期，冲突可见、可回退（复用快照/对比的语义）。

非目标：

- 实时光标级别的协同编辑（第一版不做 CRDT 字符级合并）。
- 离线长时间分叉后的自动三方合并（第一版只做画布级整份提交）。
- 服务端渲染、权限继承企业组织架构。

## 2. 数据模型（服务端视角）

以「画布」为协作单元（对应本地 `CanvasMeta` + `CanvasFlow`）：

```
Workspace（工作区）
 └─ Canvas（画布，id 全局唯一）
     ├─ meta：name / createdAt / updatedAt / deletedAt
     ├─ head：当前版本的 flow 文档指针
     └─ versions[]：追加式的版本链（与本地快照同构）
Annotation / Snapshot / TemplateBundle：挂在 Canvas 或 Workspace 下
```

关键决策：**版本链而不是行级合并**。每次保存产生一个不可变版本（与本地「快照」同构：`{nodes, edges, annotations}` + 作者 + 时间 + 说明），head 指向最新版本。这与现有 `diffFlows` 的对比能力天然对齐：冲突展示直接复用「快照对比」UI。

## 3. 同步协议（第一版：整画布提交 + 乐观锁）

```
GET  /canvases                      → 画布列表（对应本地 canvases.v1）
GET  /canvases/:id/head             → head 版本号 + 全量 flow
PUT  /canvases/:id/versions         → 提交新版本（携带 baseVersion）
     ├─ 200：baseVersion == head → 接受，head 前移
     └─ 409：baseVersion 过期 → 返回 head 全量，客户端走合并流程
POST /canvases/:id/snapshots        → 服务端快照（手动拍摄）
WS   /canvases/:id/events           → 变更通知（谁更新了哪个画布、toast 提示刷新）
```

- 客户端保存节奏不变：本地 400ms 防抖仍只写 localStorage；「云端保存」由显式动作（手动保存 / 关闭前 / 定时 30s）触发 PUT。
- 收到 409 时的合并流程见 §4。
- 批注是低冲突高频写，单独走 `POST /annotations`（追加语义，按 id 幂等）。

## 4. 冲突合并策略

按字段族分层，从低风险到高风险：

| 变更类型 | 策略 |
| --- | --- |
| 批注增删改 | 自动合并（追加语义，id 幂等） |
| 画布 meta（重命名） | last-writer-wins，可撤销 |
| 新增节点 / 连线（id 不冲突） | 自动合并（两边的 additions 都进 head） |
| 删除 vs 修改同一节点 | 保留修改，标记「删除被驳回」，toast 告知 |
| 同一节点/元素被两边改了不同字段 | 字段级合并（box 与 label 可各自生效） |
| 同一字段被两边改成不同值 | 冲突入队，用户二选一（以对比 UI 呈现） |
| 结构性操作（自动布局、批量拖动） | 整画布二选一：以我的为准 / 以远端为准（自动快照兜底） |

合并 UI 完全复用现有「快照对比」面板：左侧远端 head，右侧本地，逐项勾选采纳。合并完成后提交为新版本。

## 5. 权限模型（第一版两级，留扩展位）

```
owner   ：管理成员、删除画布、导出全部
editor  ：编辑画布内容、拍摄快照、恢复快照（恢复同样产生版本，可再回退）
viewer  ：只读 + 走查预览 + 批注（批注是 viewer 唯一写权限）
```

- 邀请：链接邀请（token 换角色），过期与撤销。
- 未来扩展位：按画布粒度授权、评论线程、审批流。当前数据模型里 `Workspace.members[]` 预留 `role` 字段即可。

## 6. 技术选型草案

- 后端：Node + SQLite（单机部署足够）→ 需要 SSO 时再换 Postgres。
- 实时：WebSocket 仅做通知（广播「画布已更新」），**不**做编辑操作流；这样服务端无编辑语义，回滚与审计都简单。
- 鉴权：第一版邮箱 magic link；会话 JWT。
- 部署：单容器 + 卷持久化；导出的单文件原型、JSON 与 PNG 导出全部保持纯前端，不经过服务端。

## 7. 本地代码的演进点（实现时要改哪里）

| 现有模块 | 演进 |
| --- | --- |
| `canvasStore.ts` | 抽象出 `CanvasBackend` 接口：localStorage 实现之外加一个 Remote 实现，UI 不感知 |
| `snapshotStore.ts` / `diffFlows` | 快照即版本；`diffFlows` 直接作为合并 UI 的对比引擎 |
| `history.ts` 撤销栈 | 撤销只作用于本地未同步变更；已提交版本用「反向版本」回退 |
| `App.tsx` 保存指示器 | 增加「云保存状态」；本地保存失败的红字语义保持不变 |
| `Preview.tsx` / 导出 | 不变（协作不影响原型与导出链路） |

## 8. 里程碑（若立项）

1. M1：账号 + 画布云备份（只上传下载，无合并）——解决「换电脑带不走」的真实痛点。
2. M2：整画布提交 + 409 合并 UI（复用对比面板）——两三人小团队可用。
3. M3：成员权限 + 通知 + 批注实时化。

每个里程碑都保持「本地优先」：断网时一切照旧，联网后同步。
