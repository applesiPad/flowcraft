## 0. 三条结论

1. **infinite-canvas 只能借「节点层」，不能借「连线层」**：它的节点确实渲染真实 React UI（`web/src/components/canvas/canvas-node.tsx:471`），但连线是固定「右侧中点 → 左侧中点」的三次贝塞尔，无箭头、无标签、无 per-edge 数据（`web/src/components/canvas/canvas-connections.tsx:23-29`；`web/src/types/canvas.ts:100-104`），且插件 SDK 只作用于节点层，无法介入边图层。
2. **tldraw 从许可上直接出局**：`LICENSE.md` 明文禁止在 Production Environment 使用、禁止干扰 License Key 校验（第 28、29 行），能力再强也不能进商业产品。
3. **主推 `@xyflow/react` 12.12.0（MIT）自研**：多 Handle（带 id/position）、`EdgeLabelRenderer`（可渲染任意 React 标签）、`markerStart/markerEnd` 箭头齐全，且 Wireflow 已用同一技术栈把同类产品做出来过；备选 maxGraph（draw.io 内核血统）与 AntV X6（有官方 React 节点包）。

## 3. 逐项一句话结论

- **@xyflow/react**：唯一"节点=React 组件、边=可完全自定义 + 可挂 React 标签"的 MIT 库，与本产品需求 1:1 对齐；代价是布局、导出、撤销、持久化要自己写（这些都是可控工作量）。
- **Excalidraw**：白板，不是流程图编辑器；元素类型是封闭联合类型（`ExcalidrawElement = 通用图形|text|linear|arrow|freedraw|image|frame|magicFrame|iframe|embeddable`），塞不进"真实界面节点"。
- **tldraw**：技术最省事，许可最致命（§5）。
- **maxGraph**：能力最接近 draw.io（顶点/边/自定义形状/XML 导入导出/100+ 样式），但面向"图形模型"而非 React 组件树，界面节点要 overlay，人才稀缺。
- **AntV X6**：`@antv/x6-react-shape` 是现成的 React 节点方案，ports 天然多锚点；国产文档、中文社区，作为备选最稳。
- **G6**：图可视化，不是编辑器，别选。
- **JointJS**：能干活，但 MPL-2.0 + 主包已改名（旧包 deprecated）+ 商业版功能诱惑，法务与长期维护成本高。
- **Drawflow**：够简单，但停更近两年，做分支标签/多锚点会一路撞墙。
- **rete**：为可视化编程而生，socket 模型对"界面跳转"是过度设计。
- **Wireflow**：**最强的可行性证据**——同样"界面截图节点 + 连线"的产品，就是 `Next + React + @xyflow/react + html-to-image` 这套栈做出来的；可直接读它验证交互细节。
- **infinite-canvas**：节点层可直接抄（真实 UI 渲染 + 插件体系），连线层必须重写（§4）。

## 4. infinite-canvas 专项结论（源码证据）

### 4.1 连线模型：单一锚点 + 固定路由

`repo/web/src/components/canvas/canvas-connections.tsx:23-29`：

```ts
const startX = from.position.x + from.width;        // 永远是源节点右侧边
const startY = from.position.y + from.height / 2;   // 永远垂直居中
const endX = to.position.x;                         // 永远是目标节点左侧边
const endY = to.position.y + to.height / 2;
const pathD = `M ${startX} ${startY} C ${startX + curvature} ${startY}, ${endX - curvature} ${endY}, ${endX} ${endY}`;
```

结论：**锚点是硬编码的 right-middle → left-middle，没有端口 id、没有方向选择、没有正交/折线路由**。拖动中的临时连线同样是这套几何（同文件 `:66-75`）。

### 4.2 边没有标签、没有箭头

同文件 `:31-58` 只输出两条 `<path>`：一条 `stroke="transparent" strokeWidth="16"` 的命中区，一条可见描边线。全文件中**不存在** `<text>` / `<textPath>` / `marker-end` / `<marker>`；全仓库 `grep -rn "marker-end\|markerEnd\|<marker" web/src` **零命中**。→ 分支条件（如「点击登录 → 成功/失败」）无处安放。

### 4.3 边的数据模型只有三个字段

`repo/web/src/types/canvas.ts:100-104`：

```ts
export type CanvasConnection = {
    id: string;
    fromNodeId: string;
    toNodeId: string;
};
```

无 `sourceHandle/targetHandle`、无 `label`、无 `metadata`、无 `type`（无法存"条件分支/失败路径"语义）。连线的创建/去重逻辑同样只有节点对维度（`repo/web/src/lib/canvas/canvas-agent-ops.ts:74-79`，仅按 `(fromNodeId,toNodeId)` 去重）。

### 4.4 插件 SDK 能补什么、补不了什么

插件契约见 `repo/plugins/canvas/README.md:95-115`（`CanvasNodeDefinition`）与 `repo/web/src/types/canvas-plugin.ts`：

| 需求 | 插件能不能补 | 证据 |
| --- | --- | --- |
| 新增节点类型、节点内渲染真实 React UI | ✅ 能 | `plugins/canvas/README.md:110` `Content: ({ctx}) => ReactNode`；`web/src/components/canvas/canvas-node.tsx:471` |
| 节点内自定义交互（按钮/表单/真界面） | ✅ 能 | `README.md:77` 示例 `onMouseDown/onClick`；`:163` 提示需 `stopPropagation` |
| 读上下游、增删连线 | ✅ 能（语义受限） | `README.md:127-129` `getUpstream/getDownstream/getConnections/applyOps` |
| 给连线加标签/条件 | ❌ 不能 | 指令集只有 `{type:"connect_nodes", fromNodeId, toNodeId}`（`README.md:142`），无 label 字段 |
| 多锚点/端口（左右上下、第 2 个输出口） | ❌ 不能 | 唯一开关是 `hasSourceHandle?: boolean`（`canvas-plugin.ts:110`；`README.md:107` 注释"右侧输出连接点"）；`canvas-node.tsx:447` 只渲染一个 `side="right"` 圆点 |
| 自定义连线样式/箭头/路由 | ❌ 不能 | 插件 API 无画布 SVG 层写入口；连线由宿主 `ConnectionPath` 独占渲染 |
| 换连线渲染器（换成 React Flow 的边） | ❌ 不能 | 插件只在节点 `Content/Panel/toolbar` 三个挂载点内渲染 |

**可用的绕行方案（工程上可行但丑）**：把"分支条件"存进源节点 `metadata`（`ctx.updateMetadata`），在节点 `Content` 底部自绘"出口 → 条件文案"列表，连线仍在宿主层裸奔。结果是标签与线不随线移动、无法在线中点编辑、无法表达一对多分支的视觉分组——对本产品核心卖点（条件分支可视化）属于硬伤。

### 4.5 额外缺口（决定工程量）

- **无全局撤销/重做**：`grep -rn "undo\|redo" web/src/components/canvas web/src/lib/canvas web/src/stores/canvas` 仅命中蒙版编辑弹窗的局部历史（`canvas-node-mask-edit-dialog.tsx:32-54`），画布本身没有 history 栈。
- **无自动布局**：`web/package.json` 依赖中无 dagre / elkjs / d3-hierarchy 等布局库。
- **持久化是浏览器本地**：`use-canvas-store.ts` 用 `localforage`（`repo/AGENTS.md` 亦声明"当前画布项目保存在浏览器本地，不要写成已支持云同步"）。
- **业务耦合重**：仓库包含 `canvas-agent/`（Codex Agent）、生图/视频/音频节点、提示词库等，剥离成本不低。

**专项建议**：把 infinite-canvas 当作**「节点渲染 + 插件体系」的参考实现**（甚至可抄 `canvas-node.tsx` 的插件容器写法），**不要作为产品底座 fork**——它的连线/撤销/布局三层恰好是本产品最吃重的三层。

## 5. 为什么不选 tldraw

`LICENSE.md`（`https://raw.githubusercontent.com/tldraw/tldraw/main/LICENSE.md`，共 70 行）原文关键句：

- 第 9 行（定义）：`"Production Environment" means any production deployment of the Software that operates on servers, cloud platforms, web applications, or where the software is used to provide functionality to end users, customers, or the public.`
- 第 28 行（禁止项）：`- Not to use the Software in Production Environments.`
- 第 29 行（禁止项）：`- Not to disable, change, or interfere with the Software's License Key enforcement.`
- 第 32 行：`- Not to distribute the Software or modifications of the Software as a standalone product, but only as part of another application.`
- 第 50 行：`The Software includes technical measures to verify License Key validity, detect deployment environments, enforce usage restrictions based on license type, and ensure proper watermark display.`
- 第 5 行：`Alternative licenses are available from tldraw for commercial and non-commercial use.`（即：要商用必须谈商业授权）

判定：本产品是"给终端用户使用的 Web 应用"，正落在第 9 行的 Production Environment 定义内，第 28 行直接禁止；即使愿意付费，也要走商务谈判（第 5 行），且第 29 行禁止我们改动其 License Key 校验逻辑——意味着**离线部署/私有化交付/内网环境**都可能触发其运行时校验，产品交付形态被供应商锁死。GitHub API 返回的 `license.spdx_id` 为 `NOASSERTION`、`npm view tldraw license` 为 `SEE LICENSE IN LICENSE.md`，与自定义商业许可一致。→ **排除，不再进入技术评估。**

## 6. 推荐路线

### 6.1 主推：@xyflow/react 12.12.0 自研（MIT）

**为什么是它**（全部有出处）：

| 能力 | 证据 |
| --- | --- |
| 节点=任意 React 组件，天然满足"节点里渲染真实界面" | `@xyflow/react` README `Key Features`：自定义节点与自定义边 |
| 一个节点多个锚点，且锚点可带 id | `npm pack @xyflow/system@0.0.76` → `dist/esm/types/handles.d.ts:56`：`id?: string \| null`（注释："optional if there is only one handle of this type"）；同文件 `:16-28` `type: 'source'\|'target'`、`position: Position` |
| 边上可挂任意 React（做条件标签/分支徽标/行内编辑） | `dist/esm/components/EdgeLabelRenderer/index.d.ts:46` `export declare function EdgeLabelRenderer(...): ReactPortal \| null` |
| 箭头 / marker | `dist/esm/components/Edges/BaseEdge.d.ts:25`（`markerStart` / `markerEnd`） |
| 连线校验（禁止自环、限制某类节点只能连某类节点） | `HandleProps.isValidConnection`（`@xyflow/system` 类型） |
| 同类产品已验证 | Wireflow `package.json`：`@xyflow/react ^12.11.6` + `html-to-image 1.11.11` + Next 16 + React 19 |
| 许可与活跃度 | MIT；38,836 stars；pushed_at 2026-10-29；npm 最后发布 2026-10-11 |

**要自己写的东西**（这就是 16–20 人日的来源）：自动布局（dagre/elkjs）、撤销重做、导出 PNG（html-to-image，Wireflow 同款）/ SVG / JSON、条件分支的数据模型、界面截图节点的素材管理、多人/持久化（如需）。

### 6.2 备选一：maxGraph（draw.io 内核）

- 优势：`README` 明示其承接 mxGraph（2020 归档）血统，`Vertices/Edges + custom shapes + 100+ 样式 + XML 导入导出`，成熟度是"做过 draw.io 级产品"的成熟度；Apache-2.0 无 copyleft 顾虑。
- 代价：面向图形模型而非 React 组件树，界面节点需要 HTML overlay（自己算变换/裁剪/事件穿透），团队要学它的命令-事务-样式模型。
- 迁移成本：若将来从 xyflow 迁到 maxGraph，**数据模型可迁移**（node/edge 是通用形态），但**节点渲染层要重写**（React 组件 → shape/overlay）、**交互层要重写**（选择/拖拽/连线手感），估算 10–14 人日返工。反向（maxGraph → xyflow）同理。→ 只有在"必须做 draw.io 级图形编辑（对齐吸附、复杂路由、分组折叠、XML 互操作）"时才值得选它。

### 6.3 备选二：AntV X6 3.1.8

- 优势：`@antv/x6-react-shape` 3.0.1（MIT，peer `@antv/x6 ^3.x`，react >=18）官方 React 节点；ports 天然支持多锚点与连接桩校验；中文文档与国内案例多。
- 代价：X6 3.x 与 2.x 教程混杂，插件（导出、对齐线、快捷键、历史）需逐个接入并验证版本匹配；Graph 命令式 API 与 React 状态同步要写胶水层。
- 迁移成本：xyflow ↔ X6 之间约 8–12 人日（节点渲染层可复用 React 组件，边/端口模型要重写）。

### 6.4 结论排序

`@xyflow/react 自研`（16–20）＞ `AntV X6`（18–24）＞ `maxGraph`（26–34）＞ `JointJS`（22–30，MPL+改名）＞ `infinite-canvas fork`（20–28，但连线/撤销/布局全要重写）＞ `Excalidraw / G6 / drawflow / rete`（不作底座）＞ `tldraw`（许可排除）。

## 7. MVP 范围与工程量拆解（估算）

**MVP 定义**（先锁范围，否则人日无意义）：无限画布 + 拖拽/缩放/多选框选 + 界面节点（内嵌真实界面截图或 HTML 预览）+ 多锚点连线 + 条件分支标签 + 自动布局 + 导出 PNG/JSON + 本地持久化 + 撤销重做。**不含**协作、评论、版本、云存储。

| 模块 | @xyflow/react 路线 | X6 | maxGraph |
| --- | --- | --- | --- |
| 画布骨架（平移/缩放/框选/小地图） | 2 | 3 | 4 |
